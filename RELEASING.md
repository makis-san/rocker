# Releasing

Rocker ships prebuilt binaries and installers for Linux, macOS, and Windows.
Everything is triggered by pushing a version tag; nothing is uploaded by hand.

## What a release produces

| Platform | Artifacts | Command-line install |
| --- | --- | --- |
| Linux (x86_64, aarch64) | `.tar.xz`, `.deb`, `.rpm`, shell installer, Homebrew formula | `curl ... \| sh`, `sudo dpkg -i`, `sudo rpm -i`, or `brew install makis-san/tap/rocker` |
| macOS (x86_64, aarch64) | `.tar.xz`, shell installer, Homebrew formula | `curl ... \| sh` or `brew install makis-san/tap/rocker` |
| Windows (x86_64) | `.zip`, `.msi`, PowerShell installer | `irm ... \| iex`, or run the `.msi` |

The `.deb`/`.rpm` also install a desktop entry, AppStream metadata, and an icon
(`packaging/linux/`), so Rocker shows up in the GNOME/KDE application menu.
A Flatpak manifest exists too (`flatpak/`) for a Flathub submission, but that's
a separate, manual process — see `flatpak/README.md`.

## How it's wired

- **`.github/workflows/release.yml`** — generated by
  [`dist`](https://opensource.axo.dev/cargo-dist/) (config in
  `dist-workspace.toml`; do not hand-edit this file, run
  `cargo xtask dist generate --mode=ci` instead and commit the result). Builds
  the raw binaries and the shell/PowerShell/MSI/Homebrew installers, and
  creates the GitHub Release.
- **`.github/workflows/linux-packages.yml`** — hand-written, runs after
  `release.yml` finishes and attaches `.deb`/`.rpm` packages (`dist` has no
  Debian/RPM support as of 0.28.7).

Both trigger on pushing a tag matching `v<major>.<minor>.<patch>` (or a bare
`<major>.<minor>.<patch>`).

## Cutting a release

1. Bump `version` under `[workspace.package]` in the root `Cargo.toml`.
2. Update `CHANGELOG.md`.
3. Commit, then tag and push: `git tag v0.1.0 && git push origin v0.1.0`.
4. Watch the `Release` and `Linux packages` workflow runs.

## One-time setup: Homebrew tap

`dist` publishes a formula on every stable release, but it needs somewhere to
push it:

1. Create an empty GitHub repo named `homebrew-tap` under `makis-san`
   (`makis-san/homebrew-tap`) — a README is enough, `dist` manages the rest.
2. Create a [personal access token](https://github.com/settings/tokens/new?scopes=repo)
   with the `repo` scope.
3. Add it as a repository secret on **this** repo named `HOMEBREW_TAP_TOKEN`.

Until that secret exists, the `publish-homebrew-formula` job in `release.yml`
will fail — the rest of the release (binaries, shell/MSI installers) still
succeeds independently.

## Why macOS builds are unsigned

Rocker is distributed as a raw binary via a `curl | sh` installer (and via
Homebrew), not as a browser-downloaded `.app`/`.dmg`. macOS only quarantines
files downloaded through APIs that call `LSSetItemAttribute` (Safari, Chrome,
Mail, etc.) — a `curl`-fetched and locally-extracted binary never gets the
`com.apple.quarantine` xattr, so Gatekeeper has nothing to block and users see
no "unidentified developer" warning.

Code signing and notarization only start to matter if Rocker is ever
distributed as a `.dmg`/`.pkg` for double-click install, or through the Mac
App Store. `dist` 0.28.7 has no built-in support for either (it only automates
Windows signing via SSL.com/Azure) — Mac notarization would need a
hand-written CI step using your own Developer ID Application certificate and
`notarytool`. Not needed for the current command-line-first distribution.

## Cross-arch Linux CI runners

`linux-packages.yml` builds `aarch64-unknown-linux-gnu` on GitHub's
`ubuntu-24.04-arm` hosted runner. If that runner class isn't available on this
repo's plan, swap it for a `cargo zigbuild` cross-compile step (see
`cargo xtask cross linux`, which already knows how) instead of a native ARM
runner.
